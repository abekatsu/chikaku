# 変更の記録

**何を変えたかではなく、なぜそう判断したかを残す。**
コードの差分は `git log` に、動く仕組みは
[implementation-status.md](implementation-status.md) にある。ここにあるのは
その手前の「実機で何が起きて、どう考えて、何を確かめたか」。

実機での検証ログをそのまま載せている。**うまくいかなかった試みも消していない。**
一度外した判断（`registerDefaultNetworkCallback` と、高度による出どころ判定）が
どう外れたかが、いちばん読む価値のある部分だと考えているため。

> 以前は変更ごとのプルリクエストの本文として書いていたものを、1 つにまとめ直した。
> 日付は当時のまま。


## 測位を GNSS 優先にし、それでも残る当てにならない点を区別して描く

Issue #13 ／ 2026-08-31 マージ

#13 への対応。**1. 当てにならない測位を見えるようにする + 2. そもそも減らす。**

#### 1. 見えるようにする

#### なぜ精度で足切りしないか

問題の10点はいずれも **100m か 300m を自称しながら 7km 外していた。**
全 233 件で閾値を検証した。

| 閾値 | 誤りが残る | 実際の遠出が残る | 外出中の点 |
|---|---|---|---|
| **500m（現状）** | 10/10 | 3/3 | 69 |
| 200m | 5/10 | 3/3 | 46 |
| 100m | 5/10 | 3/3 | 36 |
| **80m** | **0/10** | **2/3** | **18** |

**誤りを消すには 80m 未満まで下げる必要があり、そこでは外出中の点が 74% 失われる。**
屋内・地下・車内では粗い測位しか得られないため、「病院に着いた」がまるごと消える。
誤り10点を消すために正しい点を51点捨てることになる。

#### 出どころを記録する

`getProvider()` は融合済みだと `fused` としか返らないことがあるため、
**高度・速度・方位の有無**を手がかりにする。衛星測位は高度を伴い、
Wi-Fi / 基地局測位は原理的に高度を出せない。

**これは経験則であって保証ではない。** 判定の根拠になった生の値も保存し、
実機のデータを見てから引き直せるようにした。速度と方位を必須にしないのは、
静止中の衛星測位を取りこぼすため（単体テストで固定）。

`NULL` は「ネットワーク測位だった」ではなく「報告が無い」。0 で埋めると、
報告できていないだけの iOS 版と旧アプリの測位が全部「おおよその位置」になる（#4 と同じ）。
Room のマイグレーションも破壊的にせず、圏外で溜めた位置を失わないようにした。

#### ダッシュボードは消さずに描き分ける

| | |
|---|---|
| 現在地の誤差円 | 灰色の破線 |
| 地図のツールチップ | 「おおよその位置」を添える |
| 移動の経路 | その区間だけ灰色の破線 |
| 端末カード | 「おおよその位置です」と理由を出す |

**消すと「病院にいた」まで一緒に消える。** 判定は `isTrustedFix()` の1か所に置き、
地図とカードで食い違わないようにした。

#### 検証

| 対象 | 結果 |
|---|---|
| サーバー e2e | 36件（+3） |
| Android 単体 | 18件（+5） |
| iOS 契約 | 12件（省略しても壊れない） |
| `assembleRelease` / `lintVitalRelease` | 成功、lint 警告は既知の5件のみ |


#### 2. 誤りを減らす — `PRIORITY_HIGH_ACCURACY` へ切り替え

**記録するだけでは誤りは減らない。** BALANCED は公式ドキュメントに
「GPS をほとんど使わず、主に Wi-Fi と基地局の情報を使う」と明記されており、
そのままでは同じ誤りが起き続ける。

**電池は間隔で抑える。** 常時測位ではなく 5 分間隔、かつ 50m 動かない限り配信も
されないので、GNSS が連続で回るわけではない。「HIGH_ACCURACY = 電池を焼く」という
一般論は 1 秒間隔で回す前提の話で、ここには当てはまらない。

**ただし増えることは確かなので、切り替え前の基準値を実データから取った。**
位置情報と一緒に電池残量を記録してあるので、同じ計算を切り替え後に行えば比較できる。

| | BALANCED（切り替え前） |
|---|---|
| 全体の平均 | **2.50 %/h**（91.6 時間 / 229%） |
| 夜間の静止時 | 0.35 %/h |
| 最も悪い区間 | 5.13 %/h（画面操作を含む） |

**倍増程度なら許容し、3 倍を超えるなら見直す。** その場合は Activity Recognition で
移動中だけ上げる形になる。

CLAUDE.md §2.2 は BALANCED を指定していたので、撤回の理由とともに書き換えた。
**仕様書が現物と食い違ったまま残るのがいちばん困る。**

## 回線が戻ったらバックオフを捨てて送り直す

Issue #15 ／ 2026-09-21 マージ

Closes #15

#### 何が起きていたか

2026-09-07、端末が 16:20 に回線を失い、19:51 に Wi-Fi を復旧させた。
**送信は再開せず、最後の位置がサーバーに届いたのは翌 01:08**（遅延 8時間17分）。

| 測位時刻 | 受信時刻 | 遅延 |
|---|---|---|
| 16:19:55 | 16:19:57 | 0分（正常時） |
| 16:25:57 | 20:51:54 | 266分 |
| 16:51:32 | 翌 01:08:16 | **497分** |

回線が落ちていた間の挙動は正しい。壊れていたのは**回線が戻ってからの復帰**で、
原因は2つ重なっていた。

1. `UploadWorker` の指数バックオフが WorkManager の上限（5時間）まで伸び、
   **回線復帰では解除されない**
2. 毎時の `WatchdogWorker` が救済に見えて、なっていなかった。
   呼んでいた `enqueueNow` が `ExistingWorkPolicy.KEEP` なので、
   待機中のワークを見つけると何もせず返る。実機のログでは
   **203ミリ秒で `SUCCESS` を返して終わっていた**

#### 直しかた

##### `UploadScheduler.retryNow()` を追加

既存ワークの状態を見て `REPLACE` と `KEEP` を選ぶ。
判断は Android の API に依存しない純粋関数に切り出した。

```kotlin
fun shouldResetBackoff(state: WorkInfo.State?, runAttemptCount: Int): Boolean {
    // **実行中は絶対に触らない。** ワーカーはキューが空になるまで読み続けるので、
    // ここで置き換えると掃き出しの途中で毎回中断されることになる。
    if (state != WorkInfo.State.ENQUEUED) return false
    // 失敗していなければバックオフは付いていない。捨てるものが無い。
    return runAttemptCount > 0
}
```

`cancelUniqueWork` → `enqueueNow` ではなく `REPLACE` にしたのは、
取り消しと投入がひとまとめに行われるため。分けるとその隙間で `KEEP` に弾かれうる。

##### 復帰の経路を2つ用意した

| | 担当 | 遅れ |
|---|---|---|
| 即時 | `LocationTrackingService` が `registerDefaultNetworkCallback` を張り、`onAvailable` で `retryNow` | 数秒 |
| 受け皿 | `WatchdogWorker` が毎時 `retryNow` | 最大1時間 |

常駐しているのは Foreground Service だけなので、「圏外から戻った瞬間」を
拾えるのもそこしかない。キューが空なら WorkManager に触らない
（移動中は回線の切り替わりが何度も起きるため）。

`onUserUnlocked` も `retryNow` に変えた。再起動を挟むと以前のバックオフごと
復元されていることがあり、そこで待たされると再起動直後の見守りが数時間止まる。

##### バックオフのポリシー自体は変えていない

issue の案3（上限を短くする）は採らなかった。
サーバーが本当に落ちているときに叩き続ける動作になるのを避けたく、
上記2経路で復帰は確保できていると判断している。**異論があれば変更する。**

##### `onAvailable` を到達性と読み替えていない

問題の端末では、下に何も無い VPN が `VALIDATED` のまま残っていた
（`Active default network: none`、`UnderlyingNetworks: []`）。
`NetworkType.CONNECTED` は満たされ、DNS は11ミリ秒で失敗し続けた。

コールバックは「試す機会を作る」だけの役として書いてある。
外れたときはバックオフに戻り、次の機会に watchdog が拾う。

#### テスト

#### まだやっていないこと

**実機で確認していない。** 端末が繋がっていないため。

`registerDefaultNetworkCallback` が実際に `onAvailable` を返すかは未確認。

手順は `docs/implementation-status.md` §7.3 に「未検証」として残した。

#16 への参照に書き換えた。#15 の範囲外だが、同じファイルに誤った記述を残さないため。

### 追記（2026-09-19）

#### 実機検証（2026-09-19）で即時復帰の経路が一度外れた → `039b769` で修正

##### 試験1: 機内モード + Wi-Fi OFF → 復帰

復帰から **2秒**で送信。合格条件は満たすが、**これは #15 の再現ではなかった。**
完全な圏外では `NetworkType.CONNECTED` が満たされず `UploadWorker` は一度も走らない。
バックオフは 0 のまま、回線が戻れば WorkManager 自身が起動する。この経路は修正前から動いていた。

##### 試験2: Tailscale ON + Wi-Fi OFF → Wi-Fi ON（9/7 と同じ条件）

| 時刻 | 事象 |
|---|---|
| 20:29:09 | ヘルスチェックで1件投入 → `UnknownHostException`（11ms） |
| 20:30:09 | 再試行 +1分 → 失敗 |
| 20:32:09 | 再試行 +2分 → 失敗。`run_attempt_count=3` |
| **20:32:31** | **Wi-Fi 復帰** |
| 20:36:09 | 再試行 +4分 → `202` |

再現は成功。**しかし `onAvailable` は呼ばれなかった。** 送信が通ったのはたまたま
4分後に予定されていたバックオフ再試行で、9/7 のように試行回数が 8 まで伸びていれば
2時間以上待っていた。

原因は `registerDefaultNetworkCallback`。VPN が有効だとアプリの既定ネットワークは
VPN そのものになる。Wi-Fi が戻っても VPN の下が差し替わるだけで既定は変わらず、
`onAvailable` は再発火しない。

##### 修正

INTERNET 能力の `NetworkRequest` で `registerNetworkCallback` する。`NetworkRequest` は
既定で VPN を除外するため、物理回線（Wi-Fi / モバイルデータ）が上がった瞬間に反応する。

**切り替え後は未検証。** 端末を外しているため、次回繋いだときに試験2を再実行する。
手順は `docs/implementation-status.md` §7.3 に更新済み。

## 精度の申告の形で測位を疑う — 端末の自己申告をやめる

Issue #16 ／ 2026-09-21 マージ

Refs #16（A 案）。アプリ変更なし。ダッシュボードの判定だけを差し替える。

#### 何を変えたか

`isTrustedFix` の根拠を、端末の自己申告 `source_kind` から**データそのものに残っていた 2 つの手がかり**に移した。
判定は新設の `client/src/lib/trust.ts` の 1 か所にあり、地図（現在地の円・経路）と端末カードが同じ関数を使う。

| 疑う理由 | 根拠（本番 1,770 件で確認） |
|---|---|
| `database_accuracy` — 精度の申告が **100 / 200 / 300 / 400 / 500 ちょうど** | 既知の誤り 10 点が全部これ。速度が付いた 512 件のうち該当は 2 件。1 秒以内に 2 件届く 11 組はすべて「離散値 → 実数」の順 |
| `spike` — 前後の点は 1km 以内なのに、その点だけ両方から 2km 以上離れている | accuracy 56.1m で 33km 外した 9/3 の点はこれでしか拾えない。1,770 件で該当はその 1 点のみ |
| `reported_network` / `reported_unknown` — 自己申告 | 4 件しか無いが、無視する理由も無いので残す |

`source_kind` が `satellite` でも、精度の形が離散値なら疑う。561 件の `satellite` は根拠が壊れていた。

#### 本番データでの再生

```
{ database_accuracy: 284, spike: 1, trusted: 1485 }
spikes: [ '09-03 15:41:58' ]
8/29 東側 10 点: すべて database_accuracy
```

分析（#16 のコメント）で出した数字と一致する。**これは「既知の誤りを拾えた」であって「未知の誤りを拾える」ではない。** 次に誤りが見つかったら同じ再生をやり直す手順を §7.3 に書いた。

#### 拾わないもの

- 静止中に最もよく記録される精度 22.5m の点。**実は network プロバイダの出力**（`dumpsys location` で一致）だが、場所としては正しい。「network を当てる」のが目的ではないので信じる
- `source` が null（報告に対応する前のアプリ・iOS 版）。それだけでは疑わない
- スパイクは前後の点が要るので、最新位置には効かない。次の点が来るまでは判断できない

#### テスト

クライアントに `vitest` を追加した。これまでテストランナーが無かったが、この判定は実データで 2 度外れているので、テスト無しでは置けない。

```
✓ src/lib/trust.test.ts (17 tests)
```

数字はすべて本番データから取っている（9/3 の 3 点の座標、8/29 の 10 点の精度など）。

#### 残り

- **端末側の記録項目の入れ替え（#16 の B）は未着手。** 表示はこれで直るので急がない
- 8/30 16:37〜16:50 の 4 点（GPS の点から 3.4〜3.6km）は誤りかどうか未確認
